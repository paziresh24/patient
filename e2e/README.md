# E2E + Visual Regression — هارنسِ تستِ فرانت

هدف: قبل از هر تغییرِ ساختاریِ فرانت (lazy-load، defer/async، دستکاریِ critical rendering path،
code-splitting) بتوانیم در چند دقیقه ثابت کنیم **مسیرهای بحرانیِ کاربر نشکسته‌اند** — چیزی که
unit test و code review نمی‌گیرند، چون خطای hydration و شکستنِ state فقط در مرورگرِ واقعی دیده می‌شود.

این هارنس مخصوصِ یک تسک نیست؛ برای همه‌ی تغییرهای بعدیِ فرانت هم استفاده می‌شود.

## چرا Playwright (و نه Cypress + Percy/BackstopJS)

هر سه نیاز با **یک** ابزار و بدونِ سرویسِ ابریِ پولی پوشش داده می‌شود:
E2E، مقایسه‌ی بصریِ pixel-diff (`toHaveScreenshot`)، و اجرای local-first.
کمترین قطعه‌ی متحرک = کمترین چیزی که فردا بشکند.

## اجرا

```bash
npm run e2e            # کلِ تست‌ها (mobile + desktop)
npm run e2e:public     # فقط مسیرهای بدونِ لاگین — سریع‌ترین گاردِ روزمره
npm run e2e:visual     # فقط مقایسه‌ی بصری
npm run e2e:report     # گزارشِ HTML آخرین اجرا (trace/video/screenshot)
```

آدرسِ هدف با `E2E_BASE_URL` عوض می‌شود (پیش‌فرض: production):

```bash
E2E_BASE_URL=http://localhost:3000 npm run e2e:public
```

### پیش‌نیازِ نصب (نکته‌ی مهمِ محیطِ ایران)

باینریِ Chromiumِ همراهِ Playwright از `playwright.azureedge.net` دانلود می‌شود که از داخل
در دسترس نیست. برای همین `playwright.config.ts` روی **Chromeِ نصب‌شده‌ی سیستم** تنظیم شده
(`channel: 'chrome'`) و هیچ دانلودی لازم نیست. روی ماشینی که دانلود کار می‌کند، می‌شود با
`E2E_BROWSER_CHANNEL=chromium` به حالتِ استاندارد برگشت.

## تست‌های نیازمندِ لاگین

لاگینِ پذیرش۲۴ با **OTP** است و OTP نه قابلِ اتوماسیون است نه باید باشد. پس یک‌بار به‌صورتِ دستی:

```bash
npm run e2e:login      # مرورگر باز می‌شود → خودت لاگین کن → در Inspector دکمه‌ی Resume
```

session در `e2e/.auth/user.json` ذخیره می‌شود (**gitignored**) و از آن به بعد تست‌های
`appointments` و `booking-authenticated` خودکار اجرا می‌شوند. اگر این فایل نباشد آن تست‌ها
**skip** می‌شوند (نه fail) تا «نبودِ لاگین» با «خرابیِ محصول» اشتباه نشود. با انقضای session
همین دستور را دوباره بزن.

### ثبتِ نوبتِ واقعی

`booking-authenticated` به‌صورتِ پیش‌فرض تا **یک قدم قبل از ثبتِ نهایی** می‌رود — همه‌ی گاردهای
hydration را می‌گیرد بدونِ اشغالِ نوبتِ واقعی. برای اجرای کاملِ فلو:

```bash
E2E_BOOKING_SUBMIT=1 npm run e2e
```

در این حالت تست بعد از ثبت، **خودش نوبت را لغو می‌کند** و لغو را assert می‌کند (خودتمیزکن).

## قواعدِ نوشتنِ تستِ جدید (تا شکننده نشود)

1. **سلکتورِ کلاس‌محور ممنوع.** کلاس‌ها را Plasmic/Tailwind تولید می‌کنند و با هر بیلد عوض
   می‌شوند. از نقش (`getByRole`)، متنِ کاربر-دیدنی، یا الگوی `href` استفاده کن.
2. **`:visible` را جدی بگیر.** بعضی صفحات دو نمونه از یک عنصر دارند (یکی مخصوصِ لِی‌اوتِ دیگر و
   hidden). `.first()` خام روی موبایل به نمونه‌ی نامرئی می‌خورد.
3. **assert روی چیزی که در هر دو لِی‌اوت هست.** تب‌های «نظرات»/«آدرس و تلفن» فقط در موبایل
   visible‌اند؛ روی دسکتاپ در DOM هستند ولی نامرئی.
4. **به پزشکِ خاص گره نزن.** پزشک را از نتایجِ زنده انتخاب کن؛ وگرنه غیرفعال‌شدنِ یک پزشک تست را
   به‌دروغ قرمز می‌کند.
5. **انتظارِ «تغییر»، نه «تطبیق».** `waitForURL(/\/s\//)` وقتی از خودِ `/s/` شروع کرده‌ای بی‌درنگ
   برمی‌گردد و تست را flaky می‌کند.
6. **در تستِ بصری، دیتای زنده را mask کن.** هدف «آیا چیدمان جابه‌جا شد؟» است، نه «آیا محتوا عوض
   شد؟».

### بدهیِ فنیِ ثبت‌شده: نبودِ `data-testid`

در کلِ اپ **صفر** عنصر `data-testid` دارد (بررسی شد). سلکتورهای فعلی معنایی و مقاوم‌اند، ولی
پایدارترین کار افزودنِ `data-testid` به عناصرِ بحرانی (کارتِ نتیجه، دکمه‌ی دریافت نوبت، اسلاتِ
زمان، دکمه‌ی ثبتِ نهایی) است. هر تغییرِ متنِ فارسیِ این دکمه‌ها امروز می‌تواند تست را بشکند.

## مقایسه‌ی بصری — نکاتِ عملی

- baselineها per-project و per-OS ذخیره می‌شوند (`…-mobile-win32.png`). یعنی baselineهای فعلی
  **ویندوزی**‌اند؛ اگر روزی روی runnerِ لینوکسی اجرا شد باید baselineی جدا تولید شود.
- بعد از یک تغییرِ **عمدیِ** UI: `npm run e2e:visual:update` و کامیتِ تصاویرِ جدید در همان MR.
- گارد mutation-test شده: با تزریقِ ۴۰ پیکسل padding به body، تست همان‌طور که باید **قرمز شد**.

## CI

فعلاً عمداً به CI وصل **نشده** است (تصمیمِ owner: local-first، ساده شروع کنیم). وقتی خواستیم
اجباری شود، مسیرِ درست همان الگویی است که در `.gitlab-ci.yml` برای `initial-chunks` استفاده شد:
اجرا داخلِ همان `docker build`ِ اثبات‌شده — نه یک jobِ nodeِ جدا (آن مسیر با OOM و نبودِ
devDependencies قرمز شد؛ تاریخچه‌اش در ghane/docs/dev-requests/dr-08-listing-pagespeed.md §۱۳.۷).
